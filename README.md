# RiskVault iGaming — demo

Three self-contained pages. No build step, no server, no dependencies beyond a web font.

- `casino.html` — the player-facing site (lobby + a playable 3x3 slot).
- `admin-mvp.html` — the risk console, MVP scope.
- `ml-risk.html` — the ML_RISK model's actual output, day by day.

**The first two are interface: their numbers are drawn to show what the product looks like.
The third is a model: its numbers were computed by one.** Worth keeping straight — the console
shows model versions and scores, and none of them come from the model on the third page.

## Deploying on GitHub Pages

1. Put these files in the repository root (or in `/docs`).
2. Settings -> Pages -> Deploy from a branch, pick the branch and that folder.
3. Open `casino.html`, play a few rounds, then open `admin-mvp.html` in a second tab.

`index.html` redirects to the game client so the Pages root works too.

## How the link between the two pages works

The client writes canonical events (bet placed, deposit completed) into browser
storage and announces them on a broadcast channel; the console reads the same
store and re-scores the player in place. Nothing needs configuring and nothing
is sent anywhere.

Two consequences:

- Both pages must be served from the **same origin** — the same Pages site.
- Both must be open in the **same browser**. Traffic does not cross devices or
  browsers; that needs the real backend described in the technical specification.

Sessions arriving from the real client are tagged `game client` in the console,
so they stay distinguishable from the built-in emulator that keeps the screens
alive on their own.

## Demo path

1. `casino.html` -> pick a profile in the DEMO panel, bottom left -> open a game -> spin 8-10 times, deposit once after a losing run.
2. `admin-mvp.html` -> Live Monitoring -> Players online: the row carries the `game client` tag, the current game and the live score.
3. Queue -> open the alert -> case workspace: decision code, rationale, actions.
4. Journal -> Evidence exports: the whole chain as a printable extract.

Player data is a stratified sample of an anonymised public aggregate export;
aliases are pseudonymous and no personal data is present.

## `ml-risk.html` — the model, not the interface

The other two pages show what the product will look like. This one shows what the demonstration
`ML_RISK` model actually says, and it is deliberately plain: a score line, a probability line, the
day's stake, the day's events, and the features that moved the number.

Two numbers, because they answer different questions. The **score** is a percentile of the
population the model was trained on — where this player sits among the rest. The **probability** is
the calibrated chance of the harm outcome for this player alone, and it does not move when other
players are added. At the top of the range the percentile runs out of room: nine of the ten written
seeds sit at 82–99, while the probability still separates a 34 % player from a 9 % one from a 3 %
one.

747 players: ten written scenarios and 737 background players, 180 days each, every point
recomputed at that date rather than carried forward.

**Everyone on this page is invented, and the model was trained on invented people.** Distributions
were fitted to published research cohorts; no real person's data was used for training and none is
shown. The model ships at weight 0 in the product and does not reach its acceptance target — the
page says so in its own banner, with the numbers.

Generated by `ml-research/demo/scripts/build-static.ts` in the `parallax-insight` repository, which
runs every player through the same code the live demo serves. Regenerate there and copy the file
here; nothing on this page is maintained by hand.
